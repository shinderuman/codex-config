# 実装共通規則
- 言語・エコシステムで広く採用される標準的なプロジェクト構成、命名、責務分離に従う。
- 既存構成が標準から大きく外れ追加実装で負債が増える場合、勝手に構造変更せず設計判断ゲートへ戻す。
- 「動くこと」だけを完了条件にしない。
- 意味のある名前を使い`hoge` / `foo` / `bar`等を本実装へ残さない。
- 1行に複数処理を詰め込まない。制御構文本体は別行。CSSも1プロパティ1行。
- 定数・グローバル変数は意味のある単位でまとめる。
- 関数は原則30行程度を目安にするが分割で可読性が落ちる場合は行数を優先しない。
- 関数は呼び出し順に配置しcalleeをcallerの直後へ置く。
- 1回しか参照しない変数は可読性・行長・複数戻り値等の理由がなければ作らない。
- コメントは原則書かない。機械的な行数上限は設けないが、下記許可条件以外は残さない。
- コード・識別子・関数/型名・直後の処理を言い換えない。「取得/設定/構築/実行/初期化」等の要約、constructor/getter/setter/単純分岐/単純変換の説明、testのsetup/実行/assert説明は禁止。
- 許可するコメント: コードだけでは分からない実装選択理由、外部仕様・既知bug・互換性、security、非自明な不変条件、一見不要な処理を残す理由、誤変更で壊れる重要前提。shell展開・glob・文字符号化・日時・権限など固有の落とし穴は外部仕様・制約扱い。Goのpackage/exported API docもこれら許可条件を満たす内容だけ書く。
- 同じ理由を関数コメントと処理直前など複数箇所へ重複記載しない。理由は一番意味のある1箇所へ置く。
- 実装完了前に新規・変更コメントを全件削除判定し、削除して理解が変わらなければ削除、迷えば書かない。
- 削除または理由中心へ簡潔化する: コードの言い換え、明白な処理説明、期限・削除条件・責任主体のない一時コメントや履歴コメント、重複・古い・実装と不整合なコメント。
- エラーを握り潰さず原因調査に必要な情報を保持・ログ出力する。
- 原因不明の不具合では推測修正より先に実値・例外・ログを確認する。
- 一時コード、デバッグコード、プレースホルダを残さない。
- 不必要な抽象化、interface、wrapper、layerを追加しない。
- 既存の責務分割・依存方向を不用意に崩さない。
